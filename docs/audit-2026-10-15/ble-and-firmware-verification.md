# BLE transport and firmware verification — §6 of the completion directive

**Date:** 2026-10-15
**Directive point verified:** *"Verify the BLE transport and firmware from actual source. If the firmware or GATT protocol is missing, explicitly mark physical glove integration BLOCKED. Do not invent UUIDs, packet formats, sensor data, labels, model metrics or live predictions."*

## Verdict

> ## 🔴 PHYSICAL GLOVE INTEGRATION — **BLOCKED**

The block is total and it is at the source level, not a matter of configuration or
environment. There is no firmware to integrate against, and the mobile app's BLE
transport is a stub that throws. Nothing in this document is inferred, and no
identifier, frame format, sample rate or sensor value is proposed or invented.

---

## 1. The block, from four independent directions

The directive asks for verification from actual source. Four separate probes were run
against the working tree, and they agree. Any one of them would be sufficient; they
are listed together because a single probe can be satisfied by accident, and four
cannot.

### 1.1 There is no firmware in the repository

```
$ find firmware -type f
firmware/left-glove/README.md
firmware/right-glove/README.md
```

Two files. Both are READMEs, and both say the same thing:

> **This directory is empty on purpose.** No firmware has been supplied in this
> workspace, and nothing here will be invented to fill the gap — a plausible-looking
> but fabricated firmware would be worse than none, because the mobile app's BLE layer
> would then be written against a protocol that does not exist.
> — `firmware/left-glove/README.md`

A search of the whole repository for embedded source confirms it. Every `.cpp` found
is a CMake compiler-probe artefact under `apps/mobile/android/app/.cxx/`, generated by
the Android NDK build and belonging to no project code:

```
$ find . -name "*.ino" -o -name "*.cpp" -o -name "*.hpp" | grep -v node_modules
(only android/app/.cxx/**/CMakeCXXCompilerId.cpp and _CMakeLTOTest-* sources)
```

**No `.ino`, no ESP-IDF component, no sensor driver, no BLE GATT definition, no
build/flash documentation.** The ESP32-S3 firmware that `docs/ble-protocol.md`
describes as the counterparty does not exist in this workspace.

### 1.2 The transport implementation is a stub that throws

`apps/mobile/src/ble/bleTransport.ts` is 2.3 KB and its own header states the
position:

> **Real glove transport — NOT IMPLEMENTED.** […] This file is deliberately a stub
> that throws.

Both methods that would touch hardware refuse rather than pretend:

```ts
async scan(): Promise<DiscoveredGlove[]> {
  throw new ProtocolUnverifiedError();
}

async connect(_deviceId: string): Promise<void> {
  throw new ProtocolUnverifiedError();
}
```

`subscribe()` returns a no-op unsubscribe and never calls its listener, and the
transport reports itself as `{ kind: 'unavailable', reason: … }` from construction.
Its `isSynthetic` flag is `false`, with the reasoning given in the source: the stub
produces nothing at all, so marking it synthetic would put a Demo Mode badge over an
empty screen — misleading in the opposite direction.

**This is a stub, and it is recorded here as a stub.** It is not a partial
implementation, not a mock standing in for a real integration, and not something the
audit may count as BLE work done.

### 1.3 Nothing in the app ever constructs it

The strongest evidence that no BLE integration exists is that the stub is unreachable.
An exhaustive search for every construction site returns two, and both are the mock:

```
src/app/AppState.tsx:164   right: new GloveController('right', transport ?? new MockTransport('right'))
src/app/AppState.tsx:167   leftTransport ?? new MockTransport('left', { sideOffsetMs: 0 })
```

`transport` and `leftTransport` are optional injection points used by tests and the
demo. `BleTransport` is imported nowhere outside its own file. **The app's only
running transport is the synthetic simulator, and it is labelled as such in the UI**
(`MOCK_DEVICE_NAME`, and the Demo Mode badge described in `docs/ble-protocol.md:49-50`).

This is the correct state for the project to be in, and it is also why the physical
verification the directive asks about cannot be performed: there is no code path to
exercise.

### 1.4 There is no BLE capability in the app at all

Two further independent confirmations, from configuration rather than code:

**No BLE permission.** `apps/mobile/android/app/src/main/AndroidManifest.xml` declares
three permissions, and none of them is Bluetooth:

| Line | Permission |
|---|---|
| 3 | `android.permission.INTERNET` |
| 13 | `android.permission.RECORD_AUDIO` |
| 29 | `android.permission.POST_NOTIFICATIONS` |

There is **no `BLUETOOTH_SCAN`, no `BLUETOOTH_CONNECT`, and no legacy
`BLUETOOTH`/`BLUETOOTH_ADMIN`,** and no `ACCESS_FINE_LOCATION` that an Android-11-era
scan would require. `docs/glove-input-layer.md` §3 specifies the exact set that a real
integration must declare; none of it is present.

**No BLE library.** A search of `apps/mobile/package.json` for `bluetooth`, `ble` and
`react-native-ble` returns nothing. There is no dependency that could scan for or
connect to a peripheral.

**This is corroborated from outside the source tree.** The built artefact was inspected
in `docs/apk-verification-2026-10-15.md`, which recorded from `aapt2 dump badging`:

> **There is no Bluetooth permission in this APK.** That is consistent with
> `docs/glove-input-layer.md`: the app has no BLE transport implementation, no BLE
> library and no BLE permission, and the built artefact confirms all three rather than
> only the source doing so.

## 3. What this audit does not claim

Stated explicitly, because the directive names the temptation and the boundary must be
visible in the record rather than only obeyed:

- **No UUID is stated.** Not a service UUID, not a characteristic UUID, not an
  advertisement payload. Every such value in `docs/ble-protocol.md` is written as
  `<UNVERIFIED: …>` deliberately, so that a careless copy-paste cannot promote a guess
  to a shipped constant.
- **No packet or frame format is stated.** Field order, widths, signedness, byte order
  and checksum are all unknown, and none is proposed here.
- **No sample rate, MTU, or batching behaviour is stated.**
- **No sensor data is presented.** There is no capture, real or synthetic, claiming to
  be from a glove.
- **No label, vocabulary or model metric is stated.** The sign vocabulary is
  undefined, and `docs/testing-strategy.md:48-50` requires that no accuracy figure be
  cited: *"No accuracy figure exists yet … should be treated as absent, not as an
  estimate."*
- **No live prediction is claimed.** Recognition runs against synthetic frames from
  the simulator, or not at all.

The demo simulator is not evidence about the hardware in any direction. It is a
deterministic generator, it is labelled Demo Mode wherever it appears, and the
`right-glove` README is careful about the one place it could mislead: *"the right glove
is the one the mobile app's demo simulator currently models … but that is a UI default,
not a claim about the hardware."*

## 4. What the on-device session did and did not establish

A real handset session on 2026-10-15 is recorded in
`docs/device-verification-2026-10-15.md`. Relevant to this point, and not upgrading it:

- The app launched and ran, so the **absence** of BLE is not a crash — it is a missing
  capability, which is the more honest failure.
- **No glove was connected, and none could be** — there is no scan path to attempt.
- The on-device review covered three screens; the record states the rest of the
  screen set was not covered by that session, and `docs/admin-phase-final-report.md`
  separately records that the Admin half was outstanding at that time.
- No training, evaluation or inference was exercised on the device.

## 5. Owner actions to unblock

These are the only actions that move this item, in order. Items 1 and 2 are not
engineering tasks and cannot be substituted for.

1. **Supply the glove firmware source for both boards**, or state that the hardware
   does not exist. This is the single blocking input. `firmware/left-glove/README.md`
   lists exactly what the firmware must document: board and toolchain versions; the
   sensor map (5 flex channels → CD74HC4067 mux → ADS1115); I²C wiring for the ADS1115
   and MPU6050; OLED usage; BLE service/characteristic UUIDs, advertisement payload,
   connection parameters, MTU and framing; and the frame packing, byte order, sample
   rate and checksum.
2. **Answer items 1–7 of `docs/ble-protocol.md`** — from the firmware source or a live
   scan, never from inference. Item 9 (how left and right are distinguished) and item
   10 (negotiated MTU) need the hardware present.
3. **Rewrite `docs/ble-protocol.md` from the firmware**, replacing the proposal. Its
   own instruction is to rewrite rather than patch, because a proposal that has been
   partially filled in reads like a verified specification.
4. **Then** implement `BleTransport` against the real protocol, declare the permissions
   `docs/glove-input-layer.md` §3 specifies, and add the BLE client dependency.
5. **Then** capture fixtures from a real session and replay them offline, which is the
   M2 exit criterion in `docs/roadmap.md:26-28`.
6. **Then** run the physical acceptance test.

Until step 1 happens, every step after it is blocked, and this document should be
re-issued rather than amended — the verdict changes category, not degree.
